## Schedule clause eId collisions: see `lex-au/repo/FUTURE.md`, not lost Part/Division grouping

This repo previously carried (in `build/bundle.py`'s `_EID_DISAMBIG` comment) the claim that colliding schedule-unit eIds come from the converter "flattening schedule Part/Division numbering" / dropping "the source AKN's `<part>`/`<division>` grouping". That framing is wrong on two counts: there is no source AKN (the source is DOCX), and that grouping never existed in the converter's output to be dropped. The real mechanism, and the numbers, are in `../lex-au/repo/FUTURE.md`'s corrected entry (P1 investigation, 2026-09-07): ~98.7% of the 2,831 colliding eIds are `_CLAUSE_RE` / SECTION-branch false positives (amendment-instruction items, embedded schedule TOCs, un-wrapped quoted provisions), and genuine Part/Division boundary loss is only ~1.2%.

A converter-side fix (B4) is targeted for lex-au v0.10.0, not yet shipped as of lex-au v0.9.3. When it lands, this repo's `build/bundle.py` `_schedule_units`/`build_toc` will likely need updating to walk the new schedule nesting it produces, and the `~N` eId-disambiguation workaround (`_EID_DISAMBIG`) becomes largely redundant rather than the primary mitigation. Tracked as Task 22 in the same checkpoint plan (`docs/superpowers/sdd/2026-09-08-wfw-v0.3.1-phase2-4/` in the EA project wrapper) — not resolved here.

## DOCX footnotes are not extracted (6 Acts, international-instrument schedules)

lex-au's converter reads `word/document.xml` only (`docx_reader.iter_paragraphs`, `fidelity.docx_paragraphs`); `word/footnotes.xml` is never consumed, so footnote text in the source DOCX is invisible to both the converter and the fidelity audit, and never reaches this reader. Registered as known-limitation (f) in `../lex-au/repo/docs/known-limitations-schedule-and-conversion.txt` (P7 investigation, 2026-09-07) and accepted as a named carve-out rather than fixed for v0.3.1 — see the parity claim in `../lex-au/repo/README.md`.

Scope: substantive footnotes exist in exactly 6 Acts, all inside Schedules that reproduce an international instrument — `crimes-(currency)-act-1981`, `cross-border-insolvency-act-2008`, `international-fund-for-agricultural-development-act-1977`, `marine-insurance-act-1909`, `national-environment-protection-council-act-1994`, `psychotropic-substances-act-1976`. 3 of the 12 footnotes are weakly operative (glosses, reservations, cross-references qualifying a reproduced provision); 3 are explanatory. Zero endnotes and zero operative header/footer content corpus-wide (both were also investigated by P7 and ruled out as gaps).

If a future checkpoint decides to extract these, the minimal shape (from the P7 note) is: on the converter side, `docx_reader.py` opens `word/footnotes.xml` alongside `word/document.xml`, builds a `{w:id: note_text}` map (skipping `separator`/`continuationSeparator`/`continuationNotice` boilerplate types), and emits an AKN `<authorialNote marker="N">` at each `<w:footnoteReference w:id="N">`'s inline position inside the schedule content; `fidelity.py`'s `docx_paragraphs`/`akn_paragraphs` need a mirrored footnote-text branch so the audit doesn't register the newly-converted text as a spurious divergence. On this repo's side: the bundle build and reader would need to render `<authorialNote>` content (inline marker + note body, likely a footnote-style popover or endnote list per section, matching the hover-definition interaction pattern already used for defined terms). Effort estimate: M-L. Not started; no task currently scheduled for it.
